# 네트워크 아키텍처

> 구현 상태 표기: ✅ 구현+테스트 · 🟡 구현(부분 검증) · ⬜ 설계만

## 1. 전체 구성
```
 [PC 클라이언트] ─┐                       ┌─ [게임 서버 프로세스 #1: 로비]   (Godot --headless)
 [모바일 클라이언트]─┼─ HTTPS ─ [백엔드 API] ─┤─ [게임 서버 프로세스 #2: 방 A]
                  │   (로그인/친구/매칭)     └─ [게임 서버 프로세스 #N ...]
                  └──────── UDP/ENet ───────────────▲
                                              [PostgreSQL]  ← 백엔드만 접근
```
- **게임 서버 1 프로세스 = 방 1개** ✅. 가장 단순하고 장애가 격리됨. 수평 확장은 매치메이커가 프로세스를 띄우고 배정.
- **매치메이킹/계정은 백엔드(HTTP)로 분리** ⬜ — 게임 서버는 DB 접속 정보를 갖지 않는다. 결과 저장은 백엔드 내부 API로 전송.
- 클라이언트는 DB/비밀키를 절대 포함하지 않는다.

## 2. 서버 권한 모델 ✅
| 항목 | 클라이언트가 보내는 것 | 서버가 결정하는 것 |
|---|---|---|
| 이동 | 입력(방향 벡터 양자화 값, 점프/상호작용 플래그, seq) | 위치·속도·착지·리스폰 |
| 외형 | 카탈로그 인덱스 | 범위 검증 (추후 보유 아이템 대조) |
| 감정표현 | ID | 범위·쿨다운 검증 후 브로드캐스트 |
| 점수/승패 | **보내지 않음** | 서버 GameMode가 판정 (Phase 6) |

## 3. 틱과 메시지
- 물리 60 Hz (서버·클라이언트 동일). 스냅샷 30 Hz.
- ENet 채널 (`NetConfig.CH_*`):

| 채널 | 모드 | 메시지 |
|---|---|---|
| 0 | reliable | `c_hello`, `c_emote`, `c_leave`, `s_welcome`, `s_reject`, `s_player_joined/left`, `s_emote` |
| 1 | unreliable | `c_input` — 서버가 아직 ack하지 않은 입력 최대 16개를 매 틱 전송 |
| 2 | unreliable_ordered | `s_snapshot` — 오래된 스냅샷은 버려도 됨 |

- 모든 RPC는 `/root/Net`(autoload) 한 곳에 정의. 서버→클라이언트 RPC는 `authority` 모드라 클라이언트가 호출할 수 없음. `server_relay=false`로 클라이언트 간 직접 RPC 차단.

### 패킷 형식
- 입력: `[count:u8] + count × [seq:u32, move_x:s8, move_z:s8, flags:u8]` (입력당 7바이트)
- 스냅샷: `[tick:u32, count:u8] + count × [id:s32, pos:3×f32, vel:3×f32, yaw:f32, air:f32, flags:u8, ack:u32]` (플레이어당 41바이트)
- 8인 기준 스냅샷 ≈ 333B × 30Hz ≈ 10 KB/s/클라이언트. ⬜ 추후 위치 16비트 양자화·델타 압축으로 1/3 수준 목표.

## 4. 입장 절차 ✅
1. ENet 연결 → 서버는 `pending`에 등록 (5초 내 hello 없으면 `hello_timeout` 거절)
2. `c_hello{protocol, token, nickname, appearance, platform, resume?}` (`resume` = 재접속용 세션 토큰, 8장)
3. 서버 검증 순서: 타입 → 프로토콜 버전 → 토큰 → 정원 → 닉네임 → 외형 정규화
4. `s_welcome{peer_id, map_id, tick, players[], session, resumed}` + 기존 인원에게 `s_player_joined`
5. 거절 시 `s_reject(reason)` 후 0.3초 뒤 연결 종료

거절 사유: `bad_request`, `version_mismatch`, `auth_failed`, `room_full`, `bad_nickname`, `hello_timeout`, 추방: `input_flood`, `too_many_violations`

## 5. 이동 동기화 ✅
### 클라이언트 예측
매 틱 입력 생성 → 즉시 `PlayerBody.simulate()` → `(seq, input, 예측위치)` 기록 → 미확인 입력 전송.
### 서버 처리 (시간 예산 방식)
- 매 틱 credit +1 (최대 8). 입력 1개 = credit 1.
- 늦게 도착한 입력은 틱당 최대 3개까지 따라잡아 처리 → **지터가 있어도 클라이언트 예측과 정확히 일치** (테스트: 보정 192회 → 0회).
- 평균 처리 속도는 60/s를 넘을 수 없음 → 입력을 많이 보내도 빨라지지 않음 (스피드핵 불가).
- 20틱(333ms) 동안 입력이 없으면 직전 이동으로 외삽 → 랙 스위치로 공중에 멈추는 악용 방지. 외삽은 최대 30틱(0.5초)까지만, 그 뒤로는 제자리 (끊기는 중인 캐릭터가 계속 걸어가 떨어지지 않게).
### 서버 보정 (Reconciliation)
스냅샷의 내 `ack`·위치를 같은 seq의 예측 위치와 비교. 5cm 초과 오차 시 서버 상태로 되돌리고 미확인 입력을 재시뮬레이션.
### 원격 플레이어 보간
스냅샷 버퍼에서 `서버틱 추정 − 6틱(100ms)` 시점을 보간. 5m 이상 순간이동(리스폰)은 보간하지 않음.

## 6. 검증·부정행위 방지 ✅
| 위협 | 대응 | 테스트 |
|---|---|---|
| 위조 이동값 (길이 √2) | `get_move()`에서 길이 1로 제한 | 단위·통합 ✅ |
| 입력 폭주 | 초당 90개 초과분 무시, 240개 초과 시 추방 | flood 봇 추방 ✅ |
| 형식/타입 위반, seq 위조, 잘못된 감정표현 ID | 위반 카운트, 30회 시 추방 | cheat 봇 추방 ✅ |
| 구버전 클라이언트 | 프로토콜 버전 거절 | ✅ |
| hello 없이 연결 점유 | 5초 타임아웃 | ✅ |
| 클라이언트 간 RPC 중계 | `server_relay = false` | 설정 ✅ (전용 테스트 ⬜) |
| 미인증 피어의 RPC 호출 | 현재: 처리기에서 무시 / ⬜ `SceneMultiplayer.auth_callback`으로 엔진 레벨 차단 예정 | |
| 토큰 위조 | ✅ Firebase ID 토큰 RS256 서명 + aud/iss/exp/iat/sub 검증 (`FirebaseTokenVerifier`, Google 공개키 캐시). `--auth=dev`는 로컬 테스트 전용 | 단위 16개 + 목 Firebase 통합 ✅ |
| 계정 중복 접속 | 같은 uid 재접속 시 기존 세션 추방 (`logged_in_elsewhere`) | 통합 ✅ |

## 7. ENet 관련 결정 사항 (테스트로 발견)
- **패킷 스로틀 비활성화**: ENet 기본 스로틀이 RTT 변동 시 unreliable 패킷을 버려 입력이 수백 개 유실되는 현상을 확인 → `throttle_configure(5000, 32, 0)`. 전송량은 게임 측에서 제한.
- **입력 채널을 unreliable(비순서)로**: 서버가 seq로 정렬/중복 제거하므로 ENet 순서 보장 불필요.
- **미확인 입력 최대 16개 재전송**: 손실 버스트 후 첫 패킷으로 공백 복구 (Bot3 유실 47 → 7).

## 8. 재접속·장애 처리
- 연결 끊김 감지 ✅ (`peer_disconnected` / 서버: 입력이 10초 동안 없으면 끊긴 것으로 처리 / 클라이언트: 스냅샷이 4초 동안 없으면 끊긴 것으로 처리)
- 재접속 ✅ (프로토콜 3)
  - 입장 시 서버가 무작위 세션 토큰(128비트)을 `s_welcome.session`으로 준다. 재접속할 때마다 새 토큰.
  - 갑자기 끊기면 서버는 플레이어를 지우지 않고 **30초**(`RECONNECT_GRACE_MS`, `--reconnect-grace=초`) 동안 자리를 남긴다. 캐릭터는 그 자리에 멈춤(중력만), 모드 점수·목숨·체크포인트·순위는 그대로, 정원에도 포함. 다른 인원에게는 알림만.
  - 클라이언트는 같은 주소로 1초 간격 최대 25번 다시 접속하고 hello에 `resume`을 넣는다. 서버는 새 연결 번호로 자리를 옮기고(`GameMode.on_player_rekeyed`) `s_welcome{resumed: true}`를 보낸다. 다른 인원에게는 옛 번호 퇴장 + 새 번호 입장.
  - Firebase 모드: 토큰의 계정(uid)이 자리 주인과 다르면 이어받지 않음. 토큰이 없어도(새로고침) 같은 계정의 끊긴 자리가 있으면 이어서.
  - 서버가 아직 끊김을 모르는 연결(조용히 끊긴 회선)도 새 연결이 이어받고, 옛 연결은 정리.
  - 자리를 남기지 않는 경우: 추방, 거절, 서버 이동(포털·결과 후 로비), 스스로 나가기(`c_leave`, 메뉴로 나가기). 30초 안에 안 돌아오면 그때 퇴장 처리(플레이 기록 저장).
  - 끊긴 동안 라운드가 끝나 다른 인원이 로비로 이동했으면, 돌아오자마자 같은 곳으로 이동.
  - 클라우드 게이트웨이: 같은 주소(방 코드 경로)로 다시 들어오면 같은 방 서버로 연결됨. 빈 서버 종료 시간(기본 60초)이 유예 30초보다 길어서 혼자 있던 사람도 돌아올 수 있음.
- ⬜ 서버 프로세스 장애: 매치메이커 헬스체크 → 진행 중 라운드는 무효 처리 + 참여 보상 지급, 플레이어는 로비로.

## 9. 확장 (12명+)
- 현재 `--max-players` 인자로 1~32 설정 가능. 8인 동시 접속 통합 테스트 ✅.
- 12명 이상은 스냅샷 양자화 + 관심 영역(거리 기반 전송 빈도) 적용 후 부하 테스트로 결정.
